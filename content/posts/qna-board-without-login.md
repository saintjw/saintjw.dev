사이트에 방문자가 질문을 남기는 이야기방(Q&A)을 만들었습니다. 조건은 세 가지였습니다. 로그인 없이 질문할 수 있을 것, 제가 답한 질문만 공개 목록에 나올 것, 스팸이 들어와도 관리가 어렵지 않을 것입니다. 이 글에서는 그 조건을 코드로 옮기며 정한 선택들을 순서대로 적어 봅니다.

## 무엇을 만들었나

질문자는 닉네임(비워 두면 익명)과 질문만 적습니다. 질문은 처음에 `pending` 상태로 저장되고, 제가 관리자 페이지에서 답을 달면 `answered`가 됩니다. 숨기고 싶은 글은 `hidden`으로 바꿉니다. 공개 목록에는 답변이 달렸고 비공개로 보내지 않은 질문만 나옵니다.

```ts
return all.filter((q) => q.status === "answered" && !q.isPrivate);
```

저장소는 운영 환경에서는 Upstash Redis, 로컬 개발에서는 메모리를 씁니다. 코드에서는 `redis`가 있으면 그쪽에 쓰고 없으면 메모리 `Map`에 쓰는 식으로 갈라 두어서, 로컬에서는 별도 설정 없이 화면을 확인할 수 있습니다. 운영 환경인데 저장소가 연결되지 않았다면 질문을 받지 않고 "준비하고 있어요"라는 안내만 보여 줍니다. 조용히 메모리에 저장하면 서버가 재시작될 때 질문이 사라지기 때문입니다.

## 로그인이 없으니 답을 어떻게 돌려줄까

로그인이 없으면 질문자가 누구인지 알 방법이 없습니다. 그래서 질문을 저장할 때 무작위 비밀 값을 하나 만들어 질문자에게 확인 링크로 건네는 방식을 택했습니다. 비공개 질문의 답변은 이 링크로만 볼 수 있습니다.

핵심은 서버가 비밀 값 자체를 저장하지 않는다는 점입니다. 저장하는 것은 SHA-256 해시뿐이고, 링크로 들어오면 받은 값을 해시해서 저장된 값과 비교합니다. 저장소가 외부에 노출되더라도 해시만으로는 확인 링크를 만들 수 없습니다. 비교는 `timingSafeEqual`로 해서 응답 시간 차이로 값을 추측하기 어렵게 했습니다.

![서버에는 토큰의 해시만 남고 원본 토큰은 질문자의 링크에만 있다는 것을 비교한 그림](/images/posts/qna-board-without-login/token-hash.png "원본 토큰은 질문자에게만, 서버에는 해시만")

대신 단점이 있습니다. 서버에 원본이 없으니 링크를 잃어버리면 다시 보여 줄 수 없습니다. 그래서 질문이 접수된 화면에 "링크는 다시 보여 드릴 수 없으니 꼭 저장해 두세요"라고 적어 두었습니다. 편의를 조금 포기하고 개인정보 부담을 줄이는 쪽을 골랐습니다.

## 봇은 세 겹으로 막았습니다

로그인이 없는 입력창은 봇이 가장 먼저 찾아옵니다. 하나의 장치에 기대지 않고 서로 성격이 다른 세 가지를 겹쳤습니다.

![질문이 숨은 칸 확인, 횟수 제한, 자동 입력 방지를 차례로 통과해야 저장된다는 흐름 그림](/images/posts/qna-board-without-login/anti-spam-gates.png "하나라도 걸리면 멈춥니다")

첫째는 숨은 칸입니다. 화면 밖으로 밀어 둔 `website` 입력칸에 값이 들어 있으면 봇으로 보고 거절합니다. 사람은 이 칸을 볼 수 없으니 채울 일이 없습니다.

둘째는 횟수 제한입니다. 접속지(IP)마다 10분에 3번까지만 질문을 받습니다. 관리자 로그인은 15분에 5번까지입니다. 이때 IP를 그대로 저장하지 않고 해시로 바꾼 값을 제한 키로만 씁니다. 횟수만 세면 되므로 원본 주소를 갖고 있을 이유가 없습니다.

셋째는 Cloudflare Turnstile입니다. 사이트 키와 비밀 키가 연결되어 있을 때만 켜지고, 연결 전에는 앞의 두 장치만으로 동작합니다. 키 설정을 하기 전에도 개발과 확인을 이어 갈 수 있게 하려는 선택이었습니다.

여기에 내용 검사도 조금 넣었습니다. 질문은 5자 이상 1,000자 이하, 링크는 두 개까지만 허용합니다. 입력값에서는 눈에 보이지 않는 제어 문자를 지우고 앞뒤 공백을 정리합니다.

## 관리자 인증은 비밀번호 하나로

답변과 숨김, 삭제를 하는 관리자 페이지는 계정 시스템 없이 비밀번호 하나로 열립니다. 로그인에 성공하면 비밀번호로 만든 HMAC 서명을 쿠키에 담습니다.

```ts
createHmac("sha256", pw).update("qna-admin-session-v1").digest("hex");
```

쿠키는 `httpOnly`, `sameSite: "strict"`로 두고 경로는 `/qna`로 좁혔으며, 운영 환경에서는 `secure`도 켭니다. 쿠키 값이 비밀번호에서 만들어지기 때문에 비밀번호를 바꾸면 기존 로그인이 한꺼번에 풀립니다. 세션 목록을 따로 관리하지 않아도 되는 단순한 구조입니다. 관리자 동작(답변, 숨김, 삭제)은 실행할 때마다 쿠키를 다시 검사합니다. 화면에서 버튼을 가렸다는 사실에 기대지 않기 위해서입니다.

## 실패하면 쓰던 글이 사라지는 문제

처음 만든 뒤 따로 고친 부분도 있습니다. 서버 액션으로 제출한 폼은 제출이 끝나면 입력칸을 비웁니다. 그런데 횟수 제한이나 자동 입력 방지 확인에서 실패하면, 사용자는 길게 쓴 질문이 사라진 채 오류 메시지만 보게 됩니다. 폼 코드의 주석에도 이 점이 적혀 있습니다.

해결은 입력값을 React 상태로 들고 있는 것이었습니다. 질문, 닉네임, 비공개 여부를 모두 상태로 관리하고, 서버가 성공을 돌려줬을 때만 질문 칸을 비웁니다.

```tsx
if (state.ok) {
  setQuestion("");
  setIsPrivate(false);
}
```

실패했을 때는 아무것도 지우지 않으니, 사용자는 안내대로 잠시 뒤에 같은 내용을 다시 보내면 됩니다.

## 정리하며

이번 작업에서 남은 기준은 두 가지입니다. 하나는 서버가 꼭 필요하지 않은 값은 갖고 있지 않는다는 것입니다. 확인 링크의 원본 토큰도, 접속지 주소도 해시만 남겼습니다. 다른 하나는 실패했을 때의 화면도 기능의 일부라는 것입니다. 정상 경로만 확인하면 놓치기 쉬운 부분이라, 앞으로 입력 폼을 만들 때는 거절되는 경우를 먼저 떠올려 보려 합니다.

방문자의 질문은 [이야기방](/qna)에서 받고 있으니, 궁금한 점이 있으면 편하게 남겨 주세요.
